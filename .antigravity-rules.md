# Antigravity Governance Rules

> **Applies to:** All projects maintained under this governance framework.
> **Last updated:** 2026-02-28
> **Maintainer:** saintlabs-droid

---

## 1. Commit Discipline

### 1.1 One Logical Change Per Commit
Every commit must represent a **single, coherent, logical unit of change**. Do not group unrelated changes.

```
✅ feat(auth): add JWT token refresh endpoint
✅ fix(ui): correct button alignment on mobile viewport
❌ fix various bugs and update readme and add new component
```

### 1.2 Conventional Commit Types

| Type       | When to Use                                                  |
|------------|--------------------------------------------------------------|
| `feat`     | A new feature visible to end users                           |
| `fix`      | A bug fix visible to end users                               |
| `docs`     | Documentation changes only                                   |
| `style`    | Formatting, whitespace — no logic change                     |
| `refactor` | Code restructured without changing behaviour                 |
| `perf`     | Performance improvement                                       |
| `test`     | Adding or updating tests                                     |
| `chore`    | Tooling, build process, dependency management                |
| `ci`       | CI/CD pipeline changes                                       |
| `revert`   | Reverts a previous commit                                    |

### 1.3 Commit Message Format

```
<type>(<scope>): <subject>

<body — explains WHY, not WHAT. Wrap at 72 chars.>

<footer — Closes #issue, BREAKING CHANGE: description>
```

- Subject must use **imperative mood** (`add`, `fix`, `update`)
- Subject must **not** end with a period
- Subject must be **≤72 characters**
- Body is **required** for `feat`, `fix`, and `refactor` commits
- Use `.gitmessage` template: `git config commit.template .gitmessage`

### 1.4 Separate Concerns — Never Bulk Commit

| Rule                              | Example                                           |
|-----------------------------------|---------------------------------------------------|
| Separate feature from refactor    | Don't mix `feat` and `refactor` in one commit     |
| Separate docs from code           | Don't update README inside a `fix` commit         |
| Separate tests from implementation| Tests for a feature go in their own `test` commit |

## 2. Branching Strategy

```
main           ← production-ready, protected
develop        ← integration branch for all feature work
feature/*      ← new features (branches off develop)
fix/*          ← bug fixes (branches off develop or main for hotfixes)
chore/*        ← tooling, deps, config (branches off develop)
docs/*         ← documentation-only changes
refactor/*     ← code restructuring (branches off develop)
release/*      ← release preparation (branches off develop → merges to main)
hotfix/*       ← critical production fixes (branches off main)
```

### 2.1 Branch Naming Rules
- Use **kebab-case** with a descriptive slug
- Include an issue reference when applicable

```
✅ feature/user-authentication
✅ fix/login-redirect-loop
✅ chore/upgrade-node-18
✅ docs/update-api-reference
❌ new-stuff
❌ Johns-branch
❌ temp
```

### 2.2 Branch Lifecycle
1. Branch from the correct base (`develop` or `main`)
2. Make atomic commits following commit discipline
3. Keep branches short-lived — merge within the scope of a single task
4. Delete branches after merge

## 3. Pull Request Standards

### 3.1 Every PR Must Include
- A clear **title** following Conventional Commit format
- A completed **PR template** (`.github/pull_request_template.md`)
- Reference to issue(s) being closed: `Closes #123`
- **At least one** reviewer assigned

### 3.2 PR Size Rules
- PRs should be **focused** — one feature or fix per PR
- If a PR exceeds **400 lines changed**, consider breaking it up
- Draft PRs are allowed for early feedback — mark clearly with `[WIP]`

### 3.3 Review Requirements
- Minimum **1 approving review** before merge
- All CI checks must pass
- No unresolved review comments before merge
- Squash merge or rebase — no merge commits on `main`

---

## 4. Documentation Standards

- All public APIs must have docstrings
- `README.md` must be kept up to date with every feature change
- Architecture decisions should be recorded in `docs/`
- Inline comments must explain **why**, not **what**
- All documentation must use proper Markdown headings hierarchy

---

## 5. Testing Expectations

- All new features (`feat`) must include tests in a separate `test` commit
- Bug fixes must include a regression test
- Tests must be deterministic — no flaky tests allowed
- Minimum coverage threshold is enforced by CI
- Test names must be descriptive: describe the scenario, not the function

```
✅ "should return 401 when JWT token is expired"
❌ "test token"
```

---

## 6. Refactor Rules

- A `refactor` commit must **never change observable behaviour**
- Always run the full test suite after a refactor
- Refactors must be reviewed even when they "just clean things up"
- Large refactors require a `docs/ADR-<number>-<title>.md` decision record
- Never combine a refactor with a feature in the same commit

---

## 7. Enforcement

These rules are enforced via:
- `.gitmessage` — commit template
- `.githooks/pre-commit` — pre-commit hook for format validation
- CI pipeline — automated lint, test, and build gates
- PR template — structured review checklist
